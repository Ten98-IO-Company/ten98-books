# Demo data

Invented companies for demonstration and for checking ten98-books against another accounting system line by line. Every name, amount and date here is made up; none of it describes a real business, and it is for demonstration and parity checking only.

Two commands read this folder (run from the repository root, against the database in `.env`, after the user has been created in the app):

```bash
pnpm seed:demo -- --owner <email> [--company <slug> | --all] [--masters-only [--as "<company name>"]] --yes
pnpm demo:compare -- --owner <email> [--company <slug> | --all]
```

Without `--company` or `--all`, every folder is used. `seed:demo` refuses to run without `--yes`, never runs at startup or in a migration, and prints no secrets. `--masters-only` creates the company, groups and ledgers (with their openings and bill settings) and posts no vouchers, so a person can enter vouchers by hand against the same masters; see below.

## What the seeder does

For the named user, per company folder:

1. Creates the company through the application's own company-creation function (the user becomes its owner) with `company.json`'s settings.
2. Creates the groups of `groups.json` and the ledgers of `ledgers.json`, with opening balances, through the ledger module.
3. Posts `vouchers.json` in file order through the ledger module, so posting rules, numbering and the revision log apply. A voucher marked `cancelled` with lines is posted and then cancelled; one marked `cancelled` without lines is posted as cancelled without lines (a void), which takes the next number of its type and year like any voucher, so the numbers after it match the dataset's; `optional` stays optional and takes no number.

**Bills.** The seeder sends the bill keys a dataset keeps under `extras` through the ledger module's own posting path (see "Bill keys" below): a ledger's `billWise` flag, default credit days and opening bills with the ledger when it is created, and a voucher line's bill rows with the voucher. The ledger module's answers are reported: the summary counts the bill rows posted and lists the `warnings` the postings raised (`bill_attached`, `bill_over_settled`, ...) by code, each naming the voucher and bill. Bills are base currency only, so a row on a line in a foreign currency is left out and counted, and so is an against row (a settlement) naming a bill that no posted row creates (the bill belongs to a foreign-currency line, or to a voucher the dataset carries without lines, or its voucher is optional or cancelled); the line itself is posted, its amount lands on account, and the summary says how many rows were left out and why. Bills are created when a company is first seeded. A company seeded before bill rows were sent holds its vouchers without them, so the request of a voucher that now carries bill rows no longer matches what was stored; the seeder then replays that voucher as it was posted (the key proves it is this dataset's voucher), counts it as present, lists it in the summary as kept without bill rows, and goes on. Any other difference under the same key (a changed amount, date or line) still stops the seed. Seed into a new company or database to get the bills of such vouchers.

**Cost centres.** When a dataset has `costCategories.json` or `costCentres.json`, the seeder switches the company's cost centres on, creates the categories (with their `allocateRevenue` and `allocateNonRevenue`) and then the centres, parents first (a centre's optional `parent` is a centre key; it then sits in the parent's category), and sets each ledger's `extras.costCentres` (true or false; a ledger without the key keeps the ledger module's default, which takes centres on income and expense ledgers). A voucher line's `extras.costCentres` rows are sent as the line's `costAllocations` (the centre, and the base amount: a foreign-currency line carries its base-currency amount). The ledger module's answers are reported: the summary counts the rows posted and lists its `cost_*` warnings by code with the voucher and line. A row on a line whose ledger takes no cost centres is dropped by the ledger module (`cost_ignored`); the summary counts those rows and names the lines ("cost rows left out"), and the comparison names the vouchers when a centre's figure differs. A company seeded before cost rows existed holds its vouchers without them, so the request of a voucher with cost rows no longer matches what was stored; the seeder then replays that voucher in the shape it was posted (the key proves it is this dataset's voucher), counts it as present, lists it as kept without cost rows, and goes on (a voucher with bill rows and cost rows is tried complete, then without its cost rows, then without either, and each kept shape is listed). The cost masters are added to such a company, and a voucher cancelled without lines that it lacks is posted now, so it takes the next number and the later numbers do not match the dataset's (reported, not forced); seed into a new company to get the dataset's cost figures and numbers.

**Names.** Master names (groups, ledgers, cost categories, cost centres) and bill names are matched under the product's name match key (`nameMatchKey` in `src/lib/names.ts`: case, spaces and `- . / , ( ) + * ; = ~ ? { } &` are ignored), as the creation screens and the bill lists match them. A dataset with two master names equal under the key is refused when it is read, naming both spellings (a cost centre name is unique across all categories); a rerun finds a master the user spelled differently (`Rent` and `R e-n t` are one ledger); an expected bill `s i.9` is the bill `SI-9`.

**Masters only.** `--masters-only` runs steps 1 and 2 only: nothing is posted, the summary says "vouchers: not posted (masters only)", and a second run changes nothing. The company is found by its creation key, so a person may enter vouchers against the masters, and a later full `seed:demo` (without the flag) finds the same company, posts the dataset's vouchers beside theirs and sets no opening bill twice.

**Named copies (`--as`).** A dataset has one company per owner, so a second copy of its masters needs a name: `--masters-only --as "<company name>"` creates (or finds again) a separate masters-only company with that name, with the dataset's settings, groups, ledgers and openings, for the same owner. It exists for walks that must start from identical masters, for example one copy of the starter masters per keymap walk:

```bash
pnpm seed:demo -- --owner <email> --company starter-trading --masters-only --as "Keymap walk A" --yes
pnpm seed:demo -- --owner <email> --company starter-trading --masters-only --as "Keymap walk B" --yes
pnpm seed:demo -- --owner <email> --company starter-trading --yes   # the dataset's own company, with its vouchers
```

The copy is found by its own creation key (the dataset, the owner and a digest of the trimmed name, `demo:<slug>:<owner id>:as:<digest>`), so running the same command again changes nothing, a different name is another copy, and the key of the dataset's own company is never touched: the seed without `--as` still finds or creates that company and no other. A copy is found by that key only, so renaming it afterwards keeps it found by the same `--as` name. `--as` is refused without `--masters-only` (a copy never gets vouchers from the seeder), with `--all` and without `--company` (it names one copy of one dataset). The name is checked as company creation checks a name (1 to 120 characters, no control characters, surrounding spaces trimmed) and may not be the dataset's own company name, in any letter case, since that company is the one without `--as`. `demo:compare` reads the dataset's own company only and ignores named copies: with a copy alone it reports that the dataset has not been seeded, and it never compares a copy's masters.

What it cannot post is skipped and counted, never dropped silently. The summary lists: vouchers of a type ten98-books does not have (`not yet supported: 3 sales order, 4 stock journal, ...`); vouchers of a supported type that have no lines and are not cancelled (marked `extras.noAccountingEffect`: a regular voucher needs two lines here, so they cannot be represented yet); vouchers the ledger's own posting rules refuse (for example a payment that credits no cash or bank ledger), with the ledger's reason, because that is a difference from the dataset; and `items.json`, whose stock is held at its opening value until valuation is built, with that value and the item extras it does not read. Any other refusal stops the seed.

Voucher numbers: `expectedNumber` is compared for every posted voucher; the summary says how many matched and lists each that differs, naming the earlier vouchers of the same type and financial year that hold a number in the dataset but none here (skipped, refused or optional ones), which usually accounts for the whole difference. Numbers are never forced.

It is idempotent and resumable. A company is recognised, not guessed. The company created for this dataset and owner (the seeder creates it under the idempotency key `demo:<slug>:<owner id>`) is found first, so renaming it later changes nothing for `seed:demo` or `demo:compare`. Failing that, it is one of the user's companies named exactly as `company.json` names it, **and** its books carry this dataset's voucher-key namespace (every voucher is posted with the idempotency key `demo:<slug>:<voucher key>`), or it is a company this seeder created that has no vouchers yet and nothing the dataset does not define. A same-named company holding anything else is somebody's own books and is never written to (the command stops and says so). Seeding considers only companies the user owns: belonging to somebody else's copy (as viewer, editor or admin) neither blocks nor redirects it, so such a user gets a copy of their own and the other company is never written to. Two seeds at once for one user and dataset are serialised by an advisory lock, so only one creates the company. Masters (groups, ledgers, cost categories and centres, and the stock masters) are matched by name under the name match key, vouchers by key, so a second run reports "already present" and changes nothing; a run that stopped at an error resumes where it left off. Changing a voucher after it was seeded is refused (the key was used for a different voucher); seed into another user, or remove the company, instead.

It stops at the first error and names the file and key (`demo/<slug>/vouchers.json: voucher "payment-02": ...`). It applies only what ten98-books models and lists, in a summary, every feature, further file, `extras` field and `inventory` line it skipped. Voucher numbers ten98-books assigns are compared with `expectedNumber` when the file gives one; differences are reported, never forced.

## What the comparison does

Reads the seeded company through the report modules and compares it with `expected.json`, exactly in minor units: voucher counts (total and by type), trial balance totals and each listed ledger's closing balance and side, gross and net profit, and the balance sheet total (against both sides of the balance sheet). The output has three groups and every figure is in exactly one: **matches**, **differs** (each line may carry the cause when one is established, such as a dataset voucher that is not in the books, or the same amount with the opposite sign) and **not yet comparable** with the reason stated. A known unsupported cause is never counted under differs and never hidden. Counts are for the types ten98-books has: vouchers of other types and vouchers without lines that are not cancelled are taken out of the expected counts and named; vouchers cancelled without lines are posted as voids and counted. Opening stock is seeded from `items.json` (stock masters, M2b slice a): the trial balance's "Opening stock" row is compared with its value (quantity times rate per item and location, each rounded half up), and the opening-balance difference, which counts the opening stock, is compared with zero, because a dataset's ledger openings plus its opening stock balance exactly in the system the expected figures come from. Stock is not valued yet: every statement holds the opening stock in every period, so profit is the ledgers' alone. When `expected.json` gives figures excluding stock (`grossProfitExcludingStock`, `netProfitExcludingStock`) those are compared, and the stock-inclusive ones are listed as needing valuation (slice c); a balance sheet with `closingStockInAssets` and the `stockSummary` block are listed the same way. Bill figures are read from the bill reports: for each party ledger `expected.json` names under `outstanding` (and each date of `checkpoints.json`), the pending bills at that date are compared by name (under the name match key) on pending amount and side and on due date, as two lines per party ("Pending bills of ..." and "Due dates of ..."); `receivables` and `payables` (a count and a total) are compared with the pending bills of the ledgers below receivables and payables. A bill that cannot be reproduced is listed as not yet comparable, with its reason, one line per party and reason: the party has foreign-currency lines (bills are base currency only), a settlement of the bill was left out of the postings (see the seeder), or no voucher ten98-books posts creates the bill and the party has a voucher the dataset carries without lines (an expected bill that no posted row names, with no such voucher, is a difference, since a mistyped name would otherwise hide there). Bills the books hold that `expected.json` does not list are always compared, also for a party with foreign-currency lines. The count and total of a side are not yet comparable only when a row was left out on a ledger below that side's group; otherwise a gap stays a difference. A difference stays a difference even when its cause is established: the reference lists pending bills by the side they lie on, so a customer's advance counts among its payable bills, while ten98-books lists the bills of the ledgers below payables; when the gap is exactly such bills the line says so and names the vouchers. Cost centre figures are read from the cost category summary: for each centre `expected.json` names under `costCentres` (and each date of `checkpoints.json`, from the start of the period to that date), one line compares the centre's debit and credit totals ("Cost centre X"); a centre that sits under another is rolled into its top-most centre by the report, so its own figure is listed as not yet comparable. A difference stays a difference; when the dataset's own rows explain part of it, the line names the vouchers whose rows on that centre the books cannot show (the voucher was not seeded, or its ledger takes no cost centres). Blocks such as `stockSummary` and `vat` are listed with their reason. Foreign-currency datasets: ten98-books posts base-currency amounts only and has no exchange differences. An `expected.json` that restates foreign-currency ledgers at the year-end rates and adds a separate trial-balance row for the unrealised difference (`exchangeDifferences.unrealised`: `{ amount, side }`) gives totals that differ from the app's; when the difference is exactly the restatement of the foreign-currency ledgers plus that row (checked to the cent, on both trial balance sides and on both sides of the balance sheet) the foreign-currency ledger lines, the totals and the balance sheet totals are listed as not yet comparable with the arithmetic as the reason, and the row itself is listed too; otherwise they stay under differs. A realised difference is an ordinary ledger (an exchange gain and loss ledger) and is compared like any other. Vouchers dated after the period are seeded but not compared for figures. Voucher numbers are compared for every posted dataset voucher whatever its date, read back from the books: the line counts the vouchers whose number equals `expectedNumber`, names the count of those that differ with the financial years they fall in and three examples (key, date, expected, assigned). A number that differs only because earlier vouchers of the same type and financial year hold numbers in the dataset but none here (optional, refused or absent) is not yet comparable, with its reason; any other difference stays under differs. ten98-books numbers each voucher type from 1 in each financial year of the voucher's date, as the reference does ([LEDGER.md](../docs/LEDGER.md#numbering)).

Every ledger of the company is accounted for: one that `expected.json` leaves out is a difference when its closing balance is not zero, a ledger it names that the company lacks is a difference, and unlisted ledgers that close at zero are named under "Not yet comparable" with the reason. Blocks that ten98-books cannot compute yet are listed there too and never count as differences. So is a ledger that `expected.json` lists at zero while the app holds a balance, when the file's own totals are reached only with that balance (its listed closings, the opening-balance difference and the app's balances for exactly those ledgers add up to its total debit and total credit to the cent): the file's per-ledger closings are then incomplete, and the lines are listed with that reason. If the totals do not need the balance, the zero stays a difference. The first line says which company was read (a user who owns a copy and belongs to another is compared against their own). The exit code is 1 when any comparable line differs.

## Format v1

One folder per company, named by its slug. Amounts are plain decimal strings with a dot and no grouping, sign or exponent (`"1250.50"`), with at most as many decimal places as the company's `minorUnits`. Dates are `YYYY-MM-DD`. Keys are lowercase slugs (`a-z`, `0-9`, `-`, `_`), unique inside their file. Files that are not listed below, and the `extras` and `inventory` content, are accepted and kept untouched: they describe features ten98-books does not model yet. Known files are strict: an unknown key is an error that names the file and key, as is a key repeated inside one object (JSON readers would silently keep the last). A file may be at most 32 MB. The format is checked by `src/server/demo/dataset.ts`; `pnpm test` validates every folder here.

### `company.json`

```json
{ "slug": "starter-trading", "name": "Starter Trading", "secondLanguageName": "optional", "country": "AE", "baseCurrency": "AED", "minorUnits": 2,
  "financialYearStart": { "month": 1, "day": 1 }, "booksBeginning": "2026-01-01", "timeZone": "Asia/Dubai", "features": ["accounting"] }
```

`slug` equals the folder name. `baseCurrency` must be one ten98-books supports and `minorUnits` that currency's (2 or 3); `timeZone` is a named zone. `features` lists the areas the dataset uses; ten98-books models `accounting`, `billWise` and `costCentres` and lists any other (`inventory`, `multiCurrency`, ...) as skipped. `extras` is allowed.

### `groups.json` (optional)

`[ { "key", "name", "under", "nature"? } ]` for groups beyond the seeded chart. `under` is another group's key in this file (any order, no cycles) or the `system_key` of a seeded group: `branches`, `capital`, `current_assets`, `current_liabilities`, `direct_expenses`, `direct_income`, `fixed_assets`, `indirect_expenses`, `indirect_income`, `investments`, `loans`, `deferred_expenses`, `purchases`, `sales`, `suspense`, `reserves`, `bank_accounts`, `cash_in_hand`, `deposits_paid`, `advances_given`, `inventory`, `receivables`, `duties_taxes`, `provisions`, `payables`, `bank_overdraft`, `secured_loans`, `unsecured_loans`. A sub-group takes its parent's nature.

### `ledgers.json`

`[ { "key", "name", "secondLanguageName"?, "group", "standard"?, "opening"?: { "amount", "side": "Dr" | "Cr" }, "extras"? } ]`. `group` is a group key of this file or a seeded `system_key`, and is required unless the ledger is standard. `standard` (`"cash"` or `"profit_and_loss"`, each at most once) names a ledger every company already has: it is not created again, keeps its seeded name and place, and takes the opening balance if it has none. A `group` that is not the ledger's actual group is an error (the profit and loss ledger has none), and a `name` that differs from the seeded one is listed in the seed report, because the other system will carry the dataset's name.

### `vouchers.json`

An array in entry order: `{ "key", "type", "date", "status": "regular" | "cancelled" | "optional", "postDated", "narration"?, "lines": [ { "ledger", "side", "amount", "extras"? } ], "inventory"?, "extras"?, "expectedNumber"? }`. `type` is a slug. The eight voucher types ten98-books has are `contra`, `payment`, `receipt`, `journal`, `sales`, `purchase`, `credit_note` and `debit_note`; any other type (`sales_order`, `stock_journal`, `memorandum`, ...) is valid and is skipped and counted when seeding. `lines` may be empty only when the voucher is `cancelled` (a void: it takes its number and has no effect) or carries `extras.noAccountingEffect: true`, and a marked voucher carries no lines. Every `ledger` is a ledger key of `ledgers.json`; a date is on or after `booksBeginning`; every regular voucher balances; line amounts are more than zero. The ledger's posting rules still apply when seeding (for example a payment must credit a cash or bank ledger).

### `expected.json`

```json
{ "period": { "from": "2026-01-01", "to": "2026-02-03" }, "voucherCount": 18, "vouchersByType": { "payment": 5 },
  "trialBalance": { "totalDebit": "53625.00", "totalCredit": "53625.00", "ledgers": { "cash": { "closing": "9600.00", "side": "Dr" } } },
  "profitAndLoss": { "grossProfit": "3500.00", "netProfit": "-7400.00" }, "balanceSheet": { "total": "42250.00" } }
```

Only `period` is required. `numbersVerified` (optional, default false) says whether the `expectedNumber` values in `vouchers.json` were confirmed against the reference system; when it is not `true` they are the generator's own per-type sequence, and the seed summary and the comparison print them as "dataset sequence (not yet verified against the reference)" instead of "confirmed against the reference". `vouchersByType` may name any type the dataset's vouchers use. `profitAndLoss` may add `grossProfitExcludingStock` and `netProfitExcludingStock`, and `balanceSheet` `closingStockInAssets`. Keys named `source`, `report`, `note` and `voucherCountNote` only describe where a figure came from and are not listed. Conventions the comparison uses: `voucherCount` and `vouchersByType` count every undeleted voucher dated in the period, whatever its status; the trial balance is for the period, with closing balances (a zero closing matches either side); profit is positive and a loss negative, over the period (one financial year at most); the balance sheet is as at `period.to`. Ledger keys refer to `ledgers.json`. Further blocks (for example `cashFlow`) are kept and listed as not yet comparable.

### `items.json` (optional)

`{ units: [{ key, name, decimals? }], locations: [{ key, name }], stockGroups: [{ key, name }], items: [{ key, name, group?, unit?, opening?: [{ location, quantity, rate }] }] }`, other fields kept. Its shape and references are checked: an item's `group` is a stock group key, its `unit` a unit key or name, an opening's `location` a location key, rates fit the currency's decimals, and every `inventory` line of a voucher names an item and a location that exist. A unit's optional `decimals` is the number of decimal places its quantities carry (a non-negative integer, at most 4; 0 when absent): a unit measured in kilograms or litres with fractional quantities needs 1, and a system that creates it with 0 decimals rounds those quantities and reports different stock figures. The seeder switches inventory on and creates the units (symbol: `name`), locations and stock groups (at the top level) and the items with their opening rows (by rate) that the company lacks, matching each kind by name key; existing masters and the openings of existing items are kept. Item `extras` (such as a bill of materials) and the vouchers' `inventory` lines are not read yet and are listed as skipped.

### `costCategories.json`, `costCentres.json`, `currencies.json`, `checkpoints.json` (optional)

Their shape and references are checked. `costCategories.json` and `costCentres.json` are read by the seeder (see "Cost centres" above), and so is `currencies.json`: the seeder creates the currencies the company lacks (by code; `symbol` defaults to the code and `minorUnits` to 2) and the rate rows it lacks (by currency, kind and date), keeps what is already there and reports the counts; `checkpoints.json` is read by the comparison. Foreign amounts on voucher lines are still posted at their base amounts. `costCategories.json` is `[ { key, name, allocateRevenue?, allocateNonRevenue? } ]`; `costCentres.json` is `[ { key, name, category, parent? } ]` and every `category` is a cost category key and every `parent` a centre key (no cycle); names are unique under the name match key; `currencies.json` is `[ { code, name, symbol?, minorUnits?, rates?: [ { kind, date, rate } ] } ]` with a three-letter `code` that is not the company's base currency, `minorUnits` 0, 2 or 3, `kind` one of `standard`, `selling` and `buying`, a `rate` of at most 10 digits before the point and 4 after it, more than zero, and each kind and date once per currency; `checkpoints.json` is an object whose `dates` are real dates. In `vouchers.json`, a line's `extras.costCentres` (`[ { centre, amount } ]`) must name existing centres and, per category, add up to the line, a ledger's `extras.costCentres` is true or false, and `expected.json` and `checkpoints.json` name centres by key (`costCentres: { from, to, centres: { <centre key>: { debit, credit } } }` in `expected.json`, `costCentres: { <centre key>: { debit, credit } }` per date in `checkpoints.json`); `extras.currency` must be a code of `currencies.json` and `currencyAmount` and `rate` plain decimals; a voucher's `extras.party` is a ledger key; an item's `extras.billOfMaterials` names existing items. The cost centre and currency checks apply only when `costCentres.json` and `currencies.json` are present; without them a line's `extras.costCentres`, `currency` and the like are kept untouched and not checked. Bank details in a ledger's `extras.bank` use invented account numbers (the IBAN-shaped values have check digits 00 and an unallocated bank code, so they cannot belong to a real account). A foreign-currency line carries its base-currency amount in `amount`, and that is what is posted; the seed summary counts the foreign-currency and bank-detail extras it leaves out (bill rows and cost rows are posted, see above).

### Bill keys (read by the seeder)

Under `extras`, the seeder reads these keys and no others for bills; everything else under `extras` stays untouched. Two generators wrote the files and spell the same things differently, so both spellings are read and the dataset files are not renamed:

- A ledger: `billWise` (true or false; a ledger below receivables or payables is bill-wise by default), the default credit period in days `creditDays` or `creditPeriodDays`, and its opening bills in `opening.bills` or `openingBills`: `name` or `ref`, `billDate` or `date` (on or before the books begin), `amount`, optional `creditDays`, optional `side`, and `kind`, when present, must be `new`. Opening bills are on the opening balance's side, together at most the opening balance (the ledger module's rule; the validation checks it and the side).
- A voucher line: `bills`, a list of rows `{ kind | type, name | ref, amount, creditDays? }` with the kind `new`, `against`, `advance` or `on_account` (the ledger module's `new_ref`, `against_ref`, `advance`, `on_account`). A new reference and an advance may carry `creditDays` (a count of days; the party's default applies otherwise); an against row names the bill it settles; an on-account row names none. The rows of a base-currency line add up to at most the line.
- `expected.json`: `outstanding` is `{ asOf, ledgers: { <ledger key>: { bills: { bills: { <bill name>: { pending, side, dueDate } } } } } }` with the due date written like `21-Oct-26`; `receivables` and `payables` are `{ pendingBills, pendingTotal }`. `checkpoints.json` repeats `outstanding` per date as `{ <ledger key>: { bills: { <bill name>: { pending, side, dueDate } } } }`.

A malformed bill key is a validation problem naming the file, ledger or voucher and line.

### Further files

Any other `*.json` (`employees.json`, ...) is read as JSON, kept untouched and listed as skipped. A `README.md` per company is welcome: say what the company is for and where its expected figures come from.

## Adding a company

1. Make `demo/<slug>/` with `company.json`, `ledgers.json`, `vouchers.json` and `expected.json` (and `groups.json` if needed). Invent every name; use no names, text or data from any other product.
2. Run `pnpm test`: the dataset test validates every folder and names the file and key of any problem.
3. Seed it into a development database with `seed:demo` and run `demo:compare`; investigate each difference before changing `expected.json` (the figures are the reference, not whatever ten98-books computes).
