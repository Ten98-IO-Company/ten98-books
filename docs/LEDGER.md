# Ledger core (M1)

The double-entry books of one company: account groups, ledgers, voucher types, vouchers and a revision log, with the posting rules on the server and a minimal read model (trial balance, ledger balance) for verification. The app's screens consume this API through the routes below (masters first; the other company pages are still placeholders); this page documents the API, not the screens. The contract is [D-03, D-04, D-07, D-09 and D-10](DECISIONS.md); this page describes what is built.

Code: [migrations/0004_ledger.sql](../migrations/0004_ledger.sql) (tables, constraints, seeding routine), [src/server/ledger/](../src/server/ledger) (posting rules and read model), [src/server/api/masters.ts](../src/server/api/masters.ts) and [src/server/api/vouchers.ts](../src/server/api/vouchers.ts) (HTTP), [src/lib/ledger.ts](../src/lib/ledger.ts) (wire schemas and types), [src/lib/money.ts](../src/lib/money.ts) (money on the wire).

## Data model

Every table carries `company_id`, references its neighbours through composite foreign keys that include it, and forces the one company row-level security policy (D-03). The tables are listed in `accountingTables` in `src/server/tenancy.ts`, so the boot assertion refuses to start if any of them loses forced RLS or its policy.

| Table | Holds | Application role may |
|---|---|---|
| `account_group` | Group tree: parent, nature (asset, liability, income, expense), gross-profit flag, `system_key`, name, second-language name, revision | read, insert, delete, update name, parent, nature and flag |
| `ledger` | Group, `system_key`, names, opening balance (amount and Dr/Cr side as of books beginning), revision; bill-wise flag, default credit period (a count of days, weeks or months, or a fixed due date) and credit-days check | read, insert, delete, update group, names, opening and the bill-wise settings |
| `voucher_type` | Kind (one of the eight below), `system_key`, names, numbering series, revision | read, insert, rename |
| `voucher_numbering_restart` | Restart rules per voucher type and series: applicable from, starting number, periodicity; one row seeded per type (the start of the financial year in which the books begin, 1, yearly) | read, insert (seeding only) |
| `voucher_counter` | Last number issued per company, voucher type, series and numbering period (`period_start`) | read, insert, update |
| `voucher` | Type, series, number and its numbering period, date (`DATE`), narration, reference and reference date (the supplier's invoice, or the original invoice of a note), status (regular, cancelled, optional), post-dated flag, idempotency key and request hash, revision, soft-delete marker | read, insert, update lifecycle columns and the reference; never delete |
| `voucher_line` | Line order, ledger, side, base amount (`BIGINT` minor units, > 0), transaction currency, amount and FX rate, tax classification and rate | read, insert, delete (alter replaces lines) |
| `revision_log` | Who, when, entity, action, before and after snapshots | read and insert only |
| `bill` | One party ledger's bill: its name (unique per ledger ignoring case, first spelling kept) and currency | read and insert; never update or delete |
| `bill_allocation` | A bill row of a voucher line, or of a ledger's opening balance: method as entered, bill, side, amount, and its terms (due date and credit period; copied onto settlements) | read, insert, delete (with its line, or when the opening rows are replaced) |
| `ageing_bucket` | The company's ageing columns, in order; none by default | read, insert, delete |

Nature and the gross-profit flag are stored on every group and must equal the parent's (a composite foreign key with `ON UPDATE CASCADE`), so a whole sub-tree always shares its primary group's nature, and changing a primary group's nature carries its sub-groups along. A trigger refuses a group cycle.

M1 posts in the base currency only: the database requires rate 1 and equal transaction and base amounts (`voucher_line_base_currency_only`), and empty tax columns (`voucher_line_no_tax_yet`). M2 and M3 drop those two named checks; the columns are already there (D-01). Bills are base-currency only too (`bill_base_currency_only`, `bill_allocation_base_currency_only`) until foreign amounts arrive.

## Bills (M2a slice 1)

A bill is one party ledger's reference name, compared by its match key (`name_match_key` in the database, migration 0009, with its twin `nameMatchKey` in `src/lib/names.ts`, the product's general name key; the database's key alone decides identity, the twin matches names in lists on the screens): the name in lower case (simple case mapping: no accents or digits folded) without space, TAB and `- . / , ( ) + * ; = ~ ? { } &`. Every other character counts: underscore, colon, hash, backslash, at sign, exclamation mark, apostrophe, vertical bar, percent, less-than, dollar, caret, square brackets, backtick, double quote, the non-breaking space, the en dash, leading zeros (AB01 is not AB1), accents, and Arabic-Indic against ASCII digits. Evidence: import-tested and read back from the reference's outstanding export (ab1, AB-1, A-B1 and Ab-1 on one party are one bill); on screen only for settlement by name (a bill "Ab-1" settled against a typed "a.b 1" stayed one bill). The bill keeps its first spelling for display. A name of ignored characters only ("-", "( )") is valid and has an empty key, so all such names of one party are one bill, shown with the first spelling and first in name order; a name of spaces only is refused like an empty name (observed on screen: "-", ".", "( )", "- -" and "-" again became one bill "-" of 50.00). The same rule decides duplicate master names (observed on the creation screens; see "Master names", migration 0010). Its pending amount is the signed sum of its live rows (opening rows, and rows of regular, undeleted vouchers dated on or before the date). The behaviour follows what was observed on the reference workflow:

- **Methods.** A line on a bill-wise ledger may carry rows: a new reference, an advance, an against reference (a settlement naming its bill, by name or id) or on account. A new reference or advance on a name the party already has joins that bill, also after it was settled or its invoice was deleted; the same name on another party is another bill. A line without rows, and whatever its rows leave, is on account. Only the rows' net is checked against the line: it must lie between zero and the line amount (`allocation_total` otherwise), so a row on the opposite side is a bill of its own and settling more than a bill's pending is accepted.
- **Dates and terms.** A bill's date is its voucher's date; the reference date moves neither the bill date nor the credit start. A new reference or advance takes a credit period (the party's default, or one entered: days, weeks, calendar months, or a fixed due date); a settlement copies, when posted, the terms of the row that dates its bill, and keeps them. The row that dates a bill is derived (observed): its earliest-dated live new reference or advance, ties going to storage order (opening rows, then voucher, line and row); only when no new reference or advance is live does its earliest-dated live settlement date it. So a back-dated settlement never takes over the bill's dates, a second new reference dated earlier does, and when an invoice is cancelled, deleted or renamed, its settlements stand on their own, dated by themselves with their copied terms. A settlement must name a bill that still has a live entry (`bill_inactive` otherwise: the entry screen offers pending bills only), while a new reference on that name still attaches. The API accepts a settlement of a bill dated after the voucher, as the reference's import path does; the pending list for entry does not offer such a bill, as the entry screen does not.
- **Names.** A new reference without a name takes the voucher's number, or on a purchase or debit note the supplier's reference (the reference field); an optional voucher, or a purchase without a reference, must name it. The number-named rows are written just after the number is issued, the one write that follows the counter.
- **Bill-wise.** A ledger setting only (no group setting exists). New ledgers below trade receivables or payables are bill-wise by default; cash, bank and the profit and loss ledger never are, and a ledger or group holding bills does not move under the cash and bank groups. Switching it off keeps the ledger's bills pending; rows sent for it later are dropped, except that an alter keeps the rows a line already had.
- **Opening bills.** New bills only, on the opening balance's side (observed: the opening breakup has no type of reference), dated on or before the books beginning (default: the day before), together at most the opening balance; the unallocated rest is on account. Locked with the opening balances.
- **Warnings.** Behaviour the reference shows without a refusal is reproduced, and the answer says so in `warnings`: `bills_ignored` (rows dropped on a ledger that is not bill-wise), `bills_kept` (an alter kept a line's earlier rows), `bill_attached` (a new reference or advance joined another voucher's bill), `bill_over_settled` (a settlement took a bill past zero, with the excess), `bill_both_sides` (one line on both sides of one bill) and `bill_split` (an alter, cancel or delete left other vouchers' rows on a bill this voucher created).
- **Concurrency.** Ledgers are key-share locked in id order as before; new bills are inserted in (ledger, name) order with `ON CONFLICT DO NOTHING` and read back, so two postings creating one name for one party end with one bill (the second waits for the first), and two postings creating two names never wait on each other in a cycle; the counter comes next, then the number-named bills. A change to a ledger's bill-wise settings locks the ledger row first, so it waits for postings in flight.
- **Checks at commit.** M1's voucher check (at least two lines, debits equal credits, the number rules) runs unchanged on every voucher and line event. Bill rows have their own deferred check on every inserted or deleted row, over that row's line only: lines are never updated, so a line's amount can change only by deleting the line, which removes its rows too. No session setting can skip either check.

Money is `bigint` minor units in the server and the database, and a decimal string on the wire (D-07). Input amounts are checked for shape by `moneyText` and parsed with the company's currency exponent by `parseMoney` from `@ten98/runtime`, which refuses extra decimal places and amounts outside the `bigint` range instead of rounding. All sums go through the runtime's money functions. `pgTypes` in `src/server/db.ts` (from M0) reads `int8` as `bigint` and `DATE` as text on the application pools only. pg-boss opens its own connections and keeps its own parsing; Better Auth's one `int8` column (`rateLimit.lastRequest`, unused because the shared preset turns its limiter off) is declared in Drizzle's number mode, which converts the `bigint`. The ledger needed no change there. Responses format every `bigint` with `moneyToWire`, so in ledger responses every `bigint` is an amount; numbers and revisions are plain integers.

## Cost categories and cost centres (M2a slice 2)

A company keeps cost centres when an owner or admin switches the feature on (`cost-centres-setting`, off by default). A cost centre belongs to one cost category and may sit under another centre; a ledger takes cost centres when its `costCentres` flag is set. The behaviour follows what was observed on the reference workflow; rules marked *awaiting observation* are decisions the analyst has not confirmed yet.

- **Data model** (migration `0008_cost_centres.sql`). `cost_category` (a seeded row per company, `system_key 'primary'`, named "General", used on income and expense ledgers and on balance-sheet ledgers; it can be renamed but not deleted), `cost_centre` (a category, an optional parent; names are unique across all of a company's centres, so across categories) and `cost_allocation` (one row of a line's split: the line, its ledger, the category the row was saved with, the centre, a side and a base amount). Each table leads with `company_id`, references only within the company, is forced under the company policy and is in `accountingTables`. Allocation rows are never updated (no UPDATE grant): they are written and removed with their line. `company.cost_centres_enabled` and `ledger.cost_centres` are new columns; the profit and loss ledger never takes cost centres (`ledger_cost_centres_group`).
- **Defaults.** New income and expense ledgers take cost centres; other ledgers do not unless set. Migration 0008 set the flag on every existing income and expense ledger, each with a logged alter by `migration:0008_cost_centres`, and seeded the general category for every company; the company feature stays off until switched on, so nothing changes in existing books. A new category is used on income and expense ledgers and not on balance-sheet ledgers unless told (the fields `allocateRevenue` and `allocateNonRevenue`); the two settings are stored but not enforced (import-tested: a category set not to allocate non-revenue items accepted a fixed-asset line).
- **Rows on a line.** A line may carry `costAllocations: [{ costCentreId, categoryId?, amount, side? }]` (base amounts; `side` defaults to the line's). Each category used on a line nets, towards the line's side, to exactly the line amount (`allocation_total` otherwise; import-tested both under and over), so a last row may sit on the other side (observed). Categories are optional per line and a line may carry none (import-tested: that amount simply does not appear in the cost reports). On a line whose ledger takes cost centres the list states the line's rows whole: an alter that leaves it out replaces the line's rows with none. One centre appears once per category on a line (`validation`; observed: refused as a duplicate; that the rule is per category, so one centre may appear under two stored categories after a move, is *awaiting observation*). A centre with sub-centres takes rows (observed).
- **Category as saved.** `categoryId` defaults to the centre's category now. A row keeps the category it was saved with when its centre later moves to another category (observed: the voucher keeps the old category, the reports regroup the centre under the new one). An alter may re-send such a row with its stored category, on whatever line it now sits; any other category than the centre's own is refused (`validation`). *Awaiting observation*: re-saving an unchanged voucher after its centre moved.
- **Feature or flag off.** Rows sent for a line whose ledger, or company, does not take cost centres are dropped (`cost_ignored`). On an alter of a line that already had rows (the stored line of the same number and ledger, else the first stored line of its ledger that no other line claims, so rows follow their ledger when lines are inserted or removed above the only line on that ledger; among several lines of one ledger the rows go by position, so a removed or reordered line can leave one line's centres on another, with `cost_kept` or `cost_rebalanced` and `cost_dropped` for the rest, and the warning does not say which centres moved; every category still nets to its line), rows sent are accepted (`cost_kept`); with `costAllocations` left out the earlier rows are kept, and in each category the last row takes the difference to a changed line amount (`cost_rebalanced`; it turns to the other side when the difference passes it, and a row reaching zero is dropped); an empty list drops them (`cost_dropped` on the line). Stored rows of such a ledger that no line carries (its line was removed) are dropped with `cost_dropped` and no line number. Rows already stored keep counting in the reports. **Declared difference:** observed, the reference keeps such rows in its reports, hides them on the entry screen and drops them without a word when the voucher is saved again; ten98-books keeps them unless the body asks to drop them, and says so when it does. *Awaiting observation*: the company feature switched off (treated as the flag off), and a zero last row (dropped).
- **Entry prefill.** `GET ledgers/<id>/cost-default` answers the centre of the ledger's most recently entered live row (regular, undeleted vouchers; an alter enters its rows again) with the centre's category now, or null. *Awaiting observation*: which voucher the prefill comes from (most recently entered, rather than latest dated).
- **Masters.** Categories and centres are created, altered (with `revision`) and deleted like groups, with a revision log (`cost_category`, `cost_centre`). A centre created under a parent, or moved under one, goes in the parent's category; a centre that changes category and keeps its parent may end up in another category than its parent (observed). Refusals: `duplicate_name`, `cycle` (a centre under its own sub-centre), `seeded_row` (the general category), `in_use` (a category holding centres or used by rows, a centre holding sub-centres or used by rows; observed: refused); an unused centre is deleted. **Declared difference:** rows of deleted vouchers keep their centre and category in use (deleted vouchers keep their rows, as they keep their lines for ledgers), while the reference allowed the delete once the voucher was deleted. Categories and centres are two name spaces (observed: a category and a centre may share a name). Names are compared trimmed and without regard to case within each kind; the only evidence for that is the reference's import, so it is *awaiting observation* on the screens.
- **Concurrency.** A posting key-share locks the ledgers, then the centres it uses in id order, before the bills and the counter. A centre alter or delete takes the centre's row lock, so it waits for postings in flight (a delete of a used centre is then refused); a move takes the company's centre tree lock first, so two opposite moves give one success and one `cycle`. A posting that waited for a centre change reads the centre as changed.
- **Check at commit.** Allocation rows have their own deferred check on every inserted or deleted row, over that row's line only (`cost_allocation_assert_line`, through `cost_allocation_line_idx`): lines and rows are never updated, so it is complete. Without table statistics (a new table) every index that leads with `company_id` looks alike to the planner, which then read the company's rows and filtered them by line for each check (measured on a 500-line voucher: 1,000,000 row fetches). So the line index leads with the line (`voucher_id, line_no`, then category, centre and company), and the check groups by company instead of filtering on it: 2,000 fetches, with and without statistics. A row of another company in scope with the same voucher id can only make the check refuse. M1's voucher check and the bill check are unchanged. No session setting skips it.
- **Not built.** The other observed cost reports and the opening-balance report option (see [REPORTS.md](REPORTS.md)); accounting projects (a later `purpose = 'projects'` marker on a cost category, after the owner signs off on that reading of D-03; a project profit and loss would be an addition of our own, since the reference has no cost-centre profit and loss); cost allocation on the voucher entry screen (allocations are posted through the ledger module, and the masters screens for categories, centres and the company switch and the two cost report screens exist: [KEYBOARD.md](KEYBOARD.md), "Cost categories and centres"); foreign-currency allocation amounts (rows hold base amounts).

## Master names (migration 0010)

The names of groups, ledgers, voucher types, cost categories and cost centres are unique per company under the name match key (`name_match_key`, the key bills use; see "Bills"): two names equal apart from case, spaces, TAB and `- . / , ( ) + * ; = ~ ? { } &` are the same name, refused with `duplicate_name` on create and on rename; an underscore, a colon or a leading zero keeps names apart. Observed on the creation screens for groups, ledgers, voucher types and cost centres; cost categories follow the same rule (decided). A cost category and a cost centre may share a name: they are separate name spaces, as before. The rule lives in each table's unique name index (`account_group_name_idx`, `ledger_name_idx`, `voucher_type_name_idx`, `cost_category_name_idx`, `cost_centre_name_idx`, kept under their names, on `name_match_key(name)` in plain-text order); no API path looks a master up by its name. Second-language names have no uniqueness rule, as before. The seeded names stay distinct under the key in each name space, and the seeding routine finds its rows by system key, never by name.

- *Awaiting observation:* a master name made only of ignored characters ("-"). Today's rule stands: a non-space character after trimming; such a name is accepted and its key is empty, so a company holds at most one of them per kind ("-" is accepted, "." after it is `duplicate_name`, spaces only are `validation`, "_" keeps its own key; `tests/master-names.integration.ts`).
- The demo seeder (`src/server/demo/seed.ts`) finds existing masters under the key, and the demo dataset check (`src/server/demo/dataset.ts`) refuses two group, ledger, cost category or cost centre names that the key makes one ([demo/README.md](../demo/README.md)); it does not yet do so for the stock masters of `items.json`.
- **Declared difference:** in the reference, an import that creates a master whose name matches an existing one silently alters the existing master; here the API refuses it with `duplicate_name` and changes nothing.

## Currencies and rates (M2a slice 3)

Currencies are company masters keyed by a three-letter code, with three dated rate lists, and every ledger names a currency. This slice changes nothing for vouchers: a line, a bill and a bill row are still in the base currency only (`voucher_line_base_currency_only`, `bill_base_currency_only`, `bill_allocation_base_currency_only` stay), and every report is unchanged. Foreign amounts on lines, foreign bills and openings, revaluation and the exchange-difference views come with later slices.

- **Data model** (migration `0012_currencies.sql`). `currency`, primary key `(company_id, code)`: `code` (three capital letters), `symbol`, `formal_name`, an optional `iso_code`, `decimals` (0, 2 or 3: the runtime money module supports these; 1 and 4 are a declared gap), the presentation fields `in_millions`, `symbol_after`, `space_between`, `decimal_word` and `words_decimals` (defaults no, no, no, none and 2; stored, not yet applied when amounts are formatted), `system_key` (`'base'` on the seeded row), `id` (the revision log's entity id), `revision`. `exchange_rate`, primary key `(company_id, currency, kind, effective_date)`: `kind` is `standard`, `selling` or `buying`, `rate` a `numeric` more than 0 with at most 4 decimal places and 10 integer digits, kept as typed (`3.70` answers `3.70`). Both tables are forced under the company policy and listed in `accountingTables`. `ledger.currency` is `NOT NULL` (a new ledger without one takes the base; existing ledgers were backfilled with it, without a logged alter or a revision change), and `ledger`, `voucher_line`, `bill` and `bill_allocation` reference `currency` through `(company_id, currency)`, added `NOT VALID` and validated in the migration under the all-workspace scope. Before 0012 a line or a bill row could carry another currency code (the base-only checks test the rate and the amounts, not the code): the migration first stops on any such row, naming the company, the table, the count and a few of them, and applies nothing. Until foreign lines are built (slice b), the per-voucher check at commit (`voucher_assert_balanced`) also refuses a line whose currency is not the base (`voucher_line_base_currency_only`), so direct SQL cannot post one in another code the company has.
- **The base row.** The seeding routine creates it (code `company.base_currency`, decimals `currency_minor_units`, symbol and formal name the code), for new companies and, in 0012, for every existing one. Its symbol, formal name and presentation change; its code and decimals do not, and it is not deleted (`seeded_row`). It has no rate rows.
- **Symbols and codes.** A symbol is unique per company under the name match key across every symbol and every code, and a code may not equal another currency's symbol (`duplicate_name`), so a typed `USD 100` resolves one way. A currency may use its own code as its symbol, as the base row does. A symbol of ignored characters only ("...", "-") is refused (`validation`; `currency_symbol_key` in the database): its key would be empty and block every such symbol. The guard takes the company's base row `FOR NO KEY UPDATE` before it checks, so two creates or renames that would clash queue and the second is refused; postings only key-share currency rows and never wait on it (the brief named `FOR UPDATE`, which would also wait for every posting in flight; decided here, reversible).
- **Decimals and delete.** A foreign currency's decimals change, and it is deleted, only while no ledger names it (`in_use`; slice b extends this to lines, bills and openings). A ledger still being written in the currency key-shares its row, and any update or delete of a currency row waits for it, so the use check after the wait sees that ledger (`symbol_key` is a stored generated column in a non-partial unique index and the table has a BEFORE UPDATE row trigger, so PostgreSQL recomputes the generated column, treats that key as updated and takes the stronger row lock; measured: even an update of `revision` alone waits, while an explicit `FOR NO KEY UPDATE` does not). No explicit row lock is taken for it: dropping that trigger, the index or the generated column would silently weaken the lock, and the races in `tests/currencies-guards.integration.ts` pin the outcome. A decimals change is refused outside READ COMMITTED (as group changes are), because in REPEATABLE READ or SERIALIZABLE its use check would read a snapshot older than the ledger it waited for. A delete is also refused while one of its rate rows is dated on or before the locked-through date (`locked_period`); otherwise its rate rows go with it.
- **Rates.** The rate in force on a date for a kind is its row with the latest effective date on or before the date, or none before the first row (observed: a payment between two rate dates took the earlier rate, and the rates screen shows the row in force on the chosen date). Kinds are independent. Writing, changing or removing a row dated on or before `locked_through` is refused (`locked_period`), by the API and by the rate guard. A write for a date on or before the last voucher date answers `warnings: ['rates_move_reports']`: no posted figure changes, but once revaluation ships (slice c) reports from that date to the next row of the kind move with the rate. Each `POST exchange-rates` that changes something writes one revision-log entry (entity `exchange_rate`, one id per date: the uuid of the MD5 of `exchange_rate:<date>`) holding that date's rows before and after; a call that changes nothing writes none. Rates compare as numbers: 3.7 or 3.7000 sent for a stored 3.70 writes nothing, logs nothing and keeps the stored text.
- **A ledger in a foreign currency** is not bill-wise, has no credit period or credit-days check and takes no cost centres (observed: the fields leave the form), and is neither the profit and loss ledger nor under an income or expense group (ours: only capital, bank and debtor ledgers were tried in the reference); `validation` from the API, `ledger_currency_settings` and `ledger_currency_family` from the guards, including a group whose nature becomes income or expense. A new foreign ledger is not bill-wise by default, even under trade receivables or payables. Until foreign openings are built (slice b) it takes no opening balance and no opening bills (`validation` from the API, `ledger_currency_settings` from the guard; opening bills must fit the opening amount, which is then zero), and a ledger with an opening balance keeps its currency (`in_use`). It takes base-currency lines like any ledger. Its currency changes only while it has no voucher lines, opening amount, bill rows or cost rows (`in_use`); the change takes the ledger row first, as the bill-wise settings do, so a posting in flight is waited for.
- **Not built here.** Screens for currencies, rates and the ledger currency field; formatting amounts with the presentation fields; an ISO code list; the derived last-voucher rates and the entry prefill (slice b).

## Stock masters (M2b slice a, migration 0011)

Units, stock groups, stock categories, locations and stock items, with opening stock per item and location as of the books beginning. Item lines on vouchers, the stock journal and valuation are later slices; until valuation arrives the statements value stock at the opening rows ([REPORTS.md](REPORTS.md), "Stock"). Code: [migrations/0011_stock_masters.sql](../migrations/0011_stock_masters.sql), [src/server/ledger/stock-masters.ts](../src/server/ledger/stock-masters.ts), [src/server/api/stock-masters.ts](../src/server/api/stock-masters.ts), [src/lib/stock.ts](../src/lib/stock.ts).

- **Data model.** `stock_unit` (symbol, formal name, `decimals` 0 to 4, default 0), `stock_group` (tree, `add_quantities`, off by default), `stock_category` (tree), `stock_location` (tree, with one seeded row per company, `system_key 'main'`, named "Main Store"; it can be renamed, never deleted), `stock_item` (an optional group and category, a unit, an optional standard selling rate) and `stock_opening` (item and location; quantity `numeric(20,4)` above zero, rate `numeric(20,6)`, value `bigint` minor units, zero or more). Each table leads with `company_id`, references only within the company, is forced under the company policy and is in `accountingTables`. Opening rows are never updated (no UPDATE grant): an item's rows are replaced as a set. Quantities and rates are decimal strings on the wire, never floats.
- **Company switch.** `company.inventory_enabled`: on for new companies, off for companies that existed before 0011 (none held items). Owners and admins change it (`inventory-setting`; anyone else is answered `not_found`, as for the cost centres switch); switching it off is refused with `in_use` while the company has stock items, and creating an item while it is off is refused with `feature_off`. The other stock masters may be kept while it is off.
- **Names.** Each kind's names, and unit symbols, are unique per company under the name match key ("Master names"): `duplicate_name` for "z-nm 1" against "ZNM.1", or "n-os" against "Nos"; an underscore keeps names apart. Kinds are separate name spaces: an item may share its name with a stock group, a category, a location or a ledger (observed). The key is stored with each row (`name_key`, `symbol_key`, in plain-text order) and the unique indexes are on it. A create that matches an existing name is refused and changes nothing (a declared difference: the reference's import alters the existing master).
- **Opening stock.** Each row gives a location, a quantity and either a rate or a value. With a rate (at most the currency's decimal places), the value is quantity × rate rounded half-up to the currency (4,000 at 4.20 is 16,800.00). With a value, the value is the stored truth and the rate is derived by the database, value ÷ quantity to six places (3 valued at 100.00 is 33.333333); a value whose rate would reach 100,000,000,000,000 (the rate column's limit: 10^14 for one unit, or 10^10 for 0.0001) is refused with `validation` naming the row. A value of 0.00 is opening stock at no cost. The quantity carries at most its unit's decimals. One row per location. `openings` on a create or alter states the rows whole; left out on an alter, the rows stay. Rows are locked with the ledger openings: while the locked-through date reaches the books beginning, new or changed rows, and deleting an item that has rows, are refused with `locked_period` (re-sending the same rows, a rate in another spelling included, is no change, while a new rate with the same value is a change).
- **Rules the database repeats.** A unit's decimals cannot be lowered while an opening row uses it (raising them is allowed); an item's unit cannot change while it has opening rows; an opening quantity has no more places than its unit; no opening row is written or removed (an item deleted with its rows included) while the locked-through date reaches the books beginning (`stock_opening_locked`, as opening bills in 0006); the main location is not deleted and keeps its system key; no group, category or location sits under itself or its own sub-master (a transaction-scoped tree lock per kind and company serialises moves, as for account groups). A master in use is kept by the foreign keys: a unit with items, a group or category with items or sub-masters, a location with opening rows or sub-locations (`in_use`).
- **Locks.** In this order: items, units, locations. An alter or delete of a unit, item or location takes the row's `FOR UPDATE` lock; a unit delete first looks for items using the unit (`in_use` at once), so it never holds the unit while waiting for an item. An opening write holds its item (locked by the item's own write), share-locks its unit, then key-shares its locations in id order, and the database's opening guard share-locks the item and then the unit again for every row and checks the quantity against them as locked. So any writer of opening rows, the API or direct SQL, waits for a unit's decimals lowered or an item's unit changed in a transaction still open and is checked against what it committed; and lowering a unit's decimals, or changing an item's unit, waits for an opening write in flight and then sees its rows (tests in `tests/stock-masters-guards.integration.ts`, two of them by direct SQL). The guard locks row by row (an item, its unit, the next item, its unit), so a writer of several items' rows in one transaction takes the item locks and then the unit locks itself, each in id order, before inserting; two direct writers that do not can deadlock (answered as `retry`). The API writes one item's rows at a time; the item-lines slice must follow this order.
- **Index paths.** The unit check and the in-use reads seek items by unit, group or category through indexes led by that column (`stock_item_unit_idx` and its siblings; `stock_opening_location_idx` for locations), not by `company_id`: lowering an unused unit's decimals among 3,000 stocked items fetches no item row, with and without table statistics (transaction counters in `tests/stock-masters-guards.integration.ts`). 0011 has no pre-check of its own: it only adds tables, a column and the main location.
- **Revision log.** Every create, alter and delete of a unit, group, category, location or item writes one entry (`stock_unit`, `stock_group`, `stock_category`, `stock_location`, `stock_item`); an item's snapshot carries its opening rows with values as exact minor units.
- **Not built.** Screens for the stock masters (a later brief); item lines on vouchers and the stock journal (slice b); valuation and the stock reports (slice c); orders and notes (slice d); batches, price levels, stored bills of materials, reorder levels, alternate and compound units and dated standard rate lists.

## Default chart (D-10)

`ledger_seed_company(company_id)` in the migration is the one seeding routine: company creation calls it inside the company's `withCompany` transaction, and the migration runs it for every company that existed before it. It is idempotent: rows already present by `system_key` are left as the user renamed or moved them.

- 15 primary groups: Branches and Divisions, Capital, Suspense, Current Liabilities, Loans and Borrowings (liabilities); Current Assets, Fixed Assets, Investments, Deferred Expenses (assets); Sales, Direct Income, Indirect Income (income); Purchases, Direct Expenses, Indirect Expenses (expenses). Sales, Purchases, Direct Income and Direct Expenses count towards gross profit.
- 13 sub-groups: Reserves and Surplus (Capital); Bank Accounts, Cash on Hand, Deposits Paid, Loans and Advances Given, Inventory, Trade Receivables (Current Assets); Taxes and Duties, Provisions, Trade Payables (Current Liabilities); Bank Overdrafts, Secured Loans, Unsecured Loans (Loans and Borrowings).
- Two ledgers: Cash (Cash on Hand) and Profit and Loss (outside every group; the only ledger without one).
- Eight voucher types, one per kind: contra, payment, receipt, journal, sales, purchase, credit note, debit note.
- The general cost category (migration 0008) and the main location (migration 0011).

Behaviour hangs on `system_key`, never on names. Built-in rows can be renamed and given a second-language name, cannot be deleted (API check and a database trigger) and keep their nature when moved.

Behaviour families (coordinator decision under D-10, enforced in the API and the database):

- Cash and bank behaviour comes from the seeded cash and bank groups by `system_key` ancestry: a ledger is a cash or bank ledger when its group is, or sits below, `cash_in_hand`, `bank_accounts` or `bank_overdraft`.
- A built-in ledger moves only inside its behaviour family: the cash ledger stays under the cash and bank groups (moving the ledger, or a group holding it, out of them is refused), and the profit and loss ledger never has a group.
- A group's nature cannot change, by editing it or by moving it under a parent of another nature, while its sub-tree holds a built-in group or ledger, or any ledger with posted lines or a non-zero opening balance. Reclassify by moving user ledgers between groups; that stays allowed and logged. The database enforces the built-in part; the API enforces all of it.

Seeding is not written to the revision log: built-in rows are identified by their `system_key`.

## Posting rules

All in `src/server/ledger/`; screens never compute balances. Each request is one short `withCompany` transaction: viewers read, owners, admins and editors write, and a company the user cannot reach answers "not found".

- A voucher has at least two lines, every amount is more than zero and within range, and debits equal credits.
- **A void** (migration 0009): a voucher created with `status: 'cancelled'` and no lines. It takes the next number of its type in its date's period, has no accounting effect and is listed as cancelled; the revision log records its create and its key replays like any create. Lines sent with it are refused (`validation`). Like any cancelled voucher it is never altered or made regular again (decided: to record the transaction, post a new voucher); it may be deleted, and its number then stays a gap. The database exempts a voucher from the two-balanced-lines check only when the guard marked it created cancelled at insert (`created_cancelled`, set by the trigger and not updatable) and it has no lines; a cancelled voucher's lines are frozen, so a void never gains any, and a posted voucher cannot shed its lines and pass as one.
- Every ledger belongs to the company (a ledger of another company is "not found").
- The date is on or after the books-beginning date and after the company's locked-through date. A voucher already dated on or before the lock cannot be altered, cancelled or deleted, and opening balances cannot change while the lock reaches the books-beginning date (D-09).
- Contra: every line is a cash or bank ledger. Payment: at least one credit to a cash or bank ledger; it may debit one too (cash debited, bank credited). Receipt: at least one debit to a cash or bank ledger; it may credit one too. These are the reference's entry-screen rules at save; its import accepts any combination, and the API keeps the screen rules. Journal, sales, purchase, credit note and debit note accept any ledgers, cash and bank included: the reference's journal entry list only hides cash and bank ledgers until the user asks to see more, and saves them when chosen, so hiding them by default belongs to the voucher entry screen, not to the posting rules.
- The database repeats the integrity rules: a deferred constraint trigger checks at commit that every touched voucher has at least two lines, equal debits and credits, and a number exactly when it is not optional; amounts are checked positive; a counter starts at its period's first day and starting number, only moves forward by one, and keeps its period; a number is set only to the value its period's counter issued in the same transaction, never changes inside its period and is never removed; a numbered voucher's date leaves its period only together with the new period's number; restart rules are yearly and seeded only; a deleted voucher never changes; a cancelled voucher stays cancelled; a numbered voucher never becomes optional; lines of a cancelled or deleted voucher cannot be added, changed or removed.
- Group moves and nature changes are serialised per company (a transaction-scoped advisory lock, taken by the API before any row lock and again inside the database trigger, which also requires READ COMMITTED), so two opposite moves cannot both pass the cycle check. A deadlock or serialization failure answers 409 "try again"; nothing is saved.
- Every create, alter, cancel and delete of a group, ledger, voucher type or voucher writes `revision_log` in the same transaction. Snapshots are the API's own objects with amounts as exact minor-unit strings. When a nature or gross-profit change cascades to sub-groups, each sub-group's revision is bumped and its own `alter` entry is written.
- Alter and delete take the `revision` the client last read and refuse a stale one ("changed by someone else"). Altering a voucher states its whole body: `date`, `narration` (null to clear), `status`, `postDated`, `lines`; nothing falls back to a default.

## Trust boundary

Authorization is `withCompany` at every entry point. Through the API every rule on this page holds, including under concurrency: the group-tree lock serialises group moves, nature changes and every change of a ledger's group, and a nature change locks the sub-tree's ledger rows (in the same id order postings take them) before it checks for postings.

The database guards are a second line against bugs in this application, not authorization: anyone able to run SQL as `books_app` chooses the company scope (`app.company_ids`) and can act on any company they list. Every guard that reads other rows first requires the changed row's company to be inside the current scope, so clearing or changing the scope before commit makes the transaction fail instead of hiding rows from the check; as a consequence, removing a company (a cascade from its workspace) must run inside that company's scope, and nothing in M1 removes companies. For direct SQL inside the scope, the database itself refuses: an unbalanced or one-line voucher, a non-positive amount, a counter that does not move forward by exactly one or that issues a number no voucher holds, a number its counter did not issue in the same transaction or from another period's counter, a series other than its voucher type's, a changed number inside its period, a removed number, a numbered voucher's date moved into another period without that period's number, a restart rule that is not yearly or not the seeded one, any change to a deleted voucher, an un-cancelled or re-optional voucher, a line change on a cancelled or deleted voucher, a deleted built-in row, a built-in group (or a group holding a built-in ledger) changing nature, the cash ledger leaving the cash and bank groups, and a group cycle.

For bills the database also refuses: a row naming a bill of another ledger or currency, a row that does not match its line's ledger and currency, rows netting beyond their line or opening balance, a row on a cash, bank or profit and loss ledger, a new bill committed without rows (a bill can later lose its rows, when an alter moves or renames them, and then goes with its ledger if that is deleted), the deletion of a bill that has rows, a second bill for a party differing only by case, a changed bill, a due date that does not follow the stated credit period, rows changed on a cancelled or deleted voucher, an opening row dated after the books begin or changed inside the locked period, and a bill-wise cash, bank or profit and loss ledger.

Outside what the database guards cover (the API enforces these; direct SQL can break them): switching inventory off while the company has stock items; an opening stock row whose value is not its quantity times its rate (valuation and the statements read the value; the rate is for display and editing); which ledgers are bill-wise when a row is written (rows written while a ledger was bill-wise may stay after it is switched off), a nature change of a group whose ledgers have postings or opening balances; replacing a voucher's lines and cancelling it in one direct transaction (the lines change while it is still regular); the posting rules per voucher kind, the books-beginning date and the period lock; idempotency; and writing a revision log entry for each change.

**Migrations and the company policy.** The forced company policy applies to the migrator too. Anything in a migration that reads rows of a forced table (a pre-check, a backfill, a key added to an existing table or its `VALIDATE CONSTRAINT`) runs with the all-workspace scope set (`app.company_ids` listing every workspace, for that transaction only) and clears it at the end: without a scope it sees no rows, and a validation then marks a key valid without checking anything (migration 0012 had this defect in review; `tests/currencies-precheck-migration.integration.ts` pins the fix).

The period lock (locked-through date) is enforced by the application only, not by the database, apart from opening bills and opening stock rows, and the audited owner unlock (D-09) is not built: the date is set outside the API for now.

## Numbering

Numbers restart in each numbering period (D-04 as amended, migration 0007). Every voucher type holds stored restart rules (`voucher_numbering_restart`: applicable from, starting number, periodicity), and a new voucher type gets one row, seeded by the database: the start of the financial year in which the books begin, starting number 1, yearly. `ledger_numbering_rule(company, voucher type, date)` is the one place that says which period a date falls in and the period's first number: the rule in force on the date gives them. A yearly period is the company's financial year containing the date (observed also for books that begin in the middle of a financial year: the default row is dated on that year's start). Yearly is the only periodicity built: rows for daily, weekly, monthly or never, and any second row, are refused with a plain message until they are.

Numbers come from the `voucher_counter` row of the company, voucher type, series and period of the voucher's date, taken last in the posting transaction: one statement advances the counter (or starts it at the rule's starting number), the next stores the number, its period (`voucher.number_period`, the period's first day) and the date on the voucher. The database accepts only a number that counter issued in that transaction, with the period of the voucher's date. Concurrent postings of one series and period wait on that row only, and a rolled-back posting returns its number. At commit the database checks that every number a counter issued belongs to a voucher row of that type, series and period, so the only gaps are the numbers of deleted vouchers and of vouchers moved to another period. A number is unique per company, voucher type, series and period (`voucher_number_key`), not for the life of the company.

- Each voucher type counts from 1 in each financial year, in entry order. A voucher dated in the next year starts that year at 1; one dated in an earlier year, entered later, continues the earlier year's sequence.
- A deleted voucher keeps its row and number, so its number is a permanent gap in its year; the counter never rewinds, also after the year's last voucher is deleted.
- **A voucher moved to another type** (an alter with `voucherTypeId`, migration 0009; observed) takes the new type's next number in its date's period, also when the same alter moves it into another financial year, and its old number stays a gap of the old type. A cancelled voucher keeps its type (the database refuses the change). The new type's posting rules apply to its lines, and its bill rows keep their bills: a bill named after the old number keeps that name (observed: a sales voucher moved to journal took the next journal number and its bill stayed "1"). An optional voucher changes type and stays unnumbered. The database lets a numbered voucher change its type, series or number only to the number the new type's counter issued in the same transaction (`voucher_numbered`); the revision log's alter entry carries both types and numbers. The lock order is unchanged (ledgers, centres, bills, then the new type's counter), so a posting into the new type waits for the type change and takes the next number.
- An altered voucher keeps its number while its date stays in the same period. A date moved into another period takes that period's next number and leaves a gap in the old one; the database refuses a move that does not bring the new period's number (`voucher_number_period`).
- A cancelled voucher keeps its number and row (and its lines, for the record) and has no accounting effect.
- An optional voucher takes no number and has no effect until it is altered to regular, when it takes the next number of the period of its date then.
- A post-dated voucher takes its number at entry, in the year of its date, and counts from that date.
- The company's financial year start is fixed once it has restart rules or vouchers (the database refuses the change, and the application role cannot write it, nor the currency, its minor units or the books beginning). Changing it later is a future, deliberate operation that must recompute every period and counter.
- On alter, an unnamed new reference or advance stays on the bill its line already created, whatever that bill's name and whatever the voucher's number is now, so neither a date moved into another period (which gives a new number) nor a later alter renames or splits it. A name the client sends, or a changed ledger or party, decides the bill instead (a changed ledger names it by the number, as a new line would). Lines are matched by line number and ledger; reordered lines are matched by ledger only when the voucher has exactly one line on that ledger and one stored bill-creating row for it, so reordering several lines of one party can still rename. This is a decision awaiting observation of the reference.

Known behaviours, unchanged for now:

- The API accepts a date beyond the entry screen's period bound (the reference's screen refuses a date after its current period; its import accepts one). The entry screen will enforce its own bound.
- Any number issued inside a savepoint is refused (a new voucher, an optional voucher made regular, a date moved into another period): the database accepts a number only from a counter row written by the same transaction id, and a savepoint has its own. The application never numbers inside a savepoint.

Because numbers repeat across years, a number identifies a voucher only together with its year: everything that shows a number shows the voucher's date beside it (day book, ledger vouchers, the voucher view, the bills reports and their CSV), and nothing looks a voucher up by number (the API and screens use the voucher id). A sales bill named automatically takes the bare number, as the reference does, so number 1 of the next year for the same party finds the earlier year's bill "1" and joins it (`bill_attached` warning): one bill holding both invoices, dated and due as the first. Naming the bill on the voucher avoids that.

Migration 0007 gave every existing voucher type the default restart rule, kept every existing number and filed each voucher under the period of its date; each period's counter continues from the highest number present in it (deleted vouchers included). A company whose single running sequence had already crossed a year keeps those numbers, so the earlier year's next number can repeat one the later year already holds, which is legitimate from now on.

Voucher creation requires an `idempotencyKey`, unique per company: the same key with the same body returns the first result (`replayed: true`, status 200); the same key with a different body is refused (409). A transaction-scoped advisory lock on the key makes a concurrent retry wait for the first attempt.

## Read model

`trialBalance(context, from, to)` returns one typed row per ledger (opening, period debits and credits, closing, each as non-negative debit and credit amounts), totals, and the opening-balance difference, which is shown rather than blocking while a company is being set up (D-10). `ledgerBalance(context, ledgerId, from, to)` returns that ledger's row from the same shared query with a single-ledger filter, so the two always agree. The report modules in `src/server/reports/` build on that query (see [REPORTS.md](REPORTS.md)). Only regular, undeleted vouchers count. Report queries run with a 30-second statement timeout.

Opening balances are computed at report time (D-04): a balance-sheet ledger opens with its opening balance plus everything before the period; an income or expense ledger opens at zero, and everything before the period (its opening too, once the period starts after the books begin) is closed into the profit and loss ledger. Gross profit, net profit and the balance sheet are derived from the rows (nature, primary group and gross-profit flag); the golden fixture test shows how.

Response details the screens rely on:

- **`inUse`** on every row of `GET groups`, `GET groups/<id>`, `GET ledgers` and `GET ledgers/<id>`: true when a delete would be refused for use, computed by the same SQL test the delete runs. - **History routes** (`.../revisions` of groups, ledgers, voucher types, cost categories and centres, stock masters and currencies) answer 404 `not_found`, with the read route's own body, only when the company has neither a revision nor a row for that id, so a deleted master's history (revisions, no row) and an unchanged seeded master's (a row, no revision: an empty list) both answer 200. A deleted currency's history is found by its code (the last currency the company had under it). The voucher history route is unchanged here.
- **Body sizes** follow each schema's own list bound: master bodies up to 229,096 bytes (a ledger's 500 opening bills), stock master bodies up to 132,096 (an item's 500 opening rows), currency and rate bodies up to 26,624 (200 currencies), ageing columns up to 2,304 (20 columns), vouchers 256 KiB and the balance preview 128 KiB (500 lines); other bodies 8,192. A longer body answers 413; a list longer than its bound answers 400 `validation`. Each limit is stated beside its route with the bound it comes from (`tests/api-contract.integration.ts` pins both).
- **Methods.** A known path called with a method it does not accept answers 405 with an `Allow` header naming the ones it does, signed in, and on the public paths (health, status, session, setup and sign-out, the invitation and recovery routes) signed out too. Signed out, any other path answers 401 before routing, so the route map is not shown without a session. The readiness probe (`GET /api/health/ready`) uses a connection of its own, 2 seconds to connect and 2 per statement, and answers 503 with its fixed body for every failure to reach or use the database (refused, reset, timed out, shutting down or starting up, too many connections, the role refused), never 500, within about 4 seconds (`tests/readiness.integration.ts`). A path with malformed percent-encoding (`%zz`) is answered 400 by the HTTP layer (h3's request event decodes the path before any route runs), in its own shape, not ours.
- **Errors** answer `{ "error": "<plain-language message>", "code": "<reason>" }` with the same status as before. `code` is one of `ledgerErrorCodes` in `src/lib/ledger.ts` (typed `LedgerErrorCode`, shared by client and server): `validation`, `not_found`, `stale_revision`, `retry` (deadlock or serialization failure; nothing saved), `duplicate_name`, `in_use`, `seeded_row`, `nature_fixed`, `family_rule`, `cycle`, `locked_period`, `before_books_beginning`, `unbalanced`, `posting_rule` (a voucher type's cash and bank rule), `voucher_state` (cancelled, optional or numbered status forbids the change), `idempotency_mismatch` (also on company creation), `not_set_up` (409: the company has no books settings yet; members only), `allocation_total`, `bill_inactive`, `feature_off` (409: the company feature the request needs is switched off, such as inventory for a new stock item). A company the user cannot reach answers `not_found` exactly as a missing one does. A member of a company that is not set up yet gets 409 `not_set_up` on every route ([TENANCY.md](TENANCY.md)). Refusals outside the ledger (sign-in, origin check, rate limit, other areas) carry no `code`, as before.

## Voucher entry reads

Three reads for the voucher entry screen, in `src/server/ledger/voucher-entry.ts` and `src/server/api/voucher-entry.ts`. Each runs through `withCompany` in read mode (viewers may call them; a company the user cannot reach answers 404 `not_found` as everywhere), writes nothing, takes no lock beyond a plain read, and has a 5-second statement budget (D-09). An id in the path that names nothing in the company answers 404 (`Voucher type not found.`, `Ledger not found.`); an id in the query or body answers 400 `not_found` (`The voucher type was not found.`, `The ledger on line N was not found in this company.`, `The voucher was not found.`), as the posting routes do. Unknown or repeated parameters are refused (400 `validation`).

- **Next number.** The period's counter plus one, or the restart rule's starting number while the period has no counter, for the period of the date (`ledger_numbering_rule`); `periodEnd` is the end of the financial year containing the date (only yearly restart exists). It is a **preview**: nothing is reserved, so another voucher saved first takes the number, and the screen shows it as expected. It is answered for any date, also one the posting rules would refuse (before the books begin or inside the locked period). An optional voucher takes no number, so it does not move the preview.
- **Balance preview.** For each ledger named in the lines, in order of first appearance: its closing balance from the start of the date's financial year to the date in the shared read model (the trial balance's figure, so the two always agree), minus the stored lines of `voucherId` when that voucher counts at the date (regular, undeleted, dated on or before it; an earlier year's income or expense line comes off the profit and loss ledger, where it sits by then), plus the draft lines. Signed: positive on the debit side, negative on the credit side. Lines are checked as posting checks them (amount format and decimal places, more than zero, debit and credit totals inside the `bigint` range, a ledger of the company, checked before the aggregate runs, at most 500; a resulting balance beyond that range is refused too), but the draft may be unbalanced or break a voucher type's cash and bank rule: it is not posted. A request body is at most 128 KB.
- **Counter ledger.** From the most recently entered regular, undeleted voucher of the type with a line on the ledger on that side (latest `created_at`, then id; cancelled, optional and deleted vouchers are skipped), its first line on the other side by line number; `null` when the ledger has no such voucher. Observed: a ledger used before proposes the counter ledger of its most recent voucher, not its most frequent one, and only in double entry (single entry proposes nothing, so the screen does not call this read there). Entry order and date order coincided in the observation; entry order is used.

Measured on a generated company of 52,784 voucher lines (13,196 four-line vouchers over two financial years; the busiest ledger has 13,196 lines) as `books_app` with row-level security, PostgreSQL 18, EXPLAIN ANALYZE inside `withCompany`; statement counts are those of the read itself, after `withCompany`'s membership lock and scope and the company settings read, and include the `SET LOCAL` budget:

| Read | Statements | Query time | HTTP in process, median of 21 |
|---|---|---|---|
| Next number | 2 | 1.5 ms | 8.8 ms |
| Balance preview (3 lines, 2 ledgers, with `voucherId`) | 4 | 0.02 ms (the draft's ledgers), 53.1 ms (the read model's one set-based query) and 0.04 ms (the stored voucher) | 55.0 ms |
| Counter ledger, busiest ledger, found | 3 | 0.03 ms (existence) and 4.8 ms (index `voucher_line_ledger_idx`, join, top-1) | 12.9 ms |
| Counter ledger, a voucher type with no vouchers | 3 | 0.03 ms | 9.0 ms |

The balance preview's cost is the trial balance's; see "Known limits".

## Known limits

- **The balance preview reads the whole company.** Every call aggregates every ledger's lines up to the date (the trial balance query), about 53 ms at about 50,000 lines in the measurement above, and the cost grows with the company's whole history, not with the draft. The later fix is a list of ledgers in the read model's single-ledger mode (`ledgerRows` with several ledgers, the profit and loss ledger still reading all income and expense), not built yet.
- **Bill checks on a new table (fixed by migration 0009).** Before 0009 the two deferred bill checks read a company's rows for each check while `bill_allocation` had no statistics: a 500-line voucher with 250 new bills fetched 93,875 rows at commit. Migration 0009 leads the line and bill indexes with the line and the bill (`(voucher_id, line_no)`, `(bill_id)`) and drops the company filter from the two checks, which now fetch 500 rows with and without statistics, also for a second company posting into a table that holds the first one's rows (`tests/bills-timing.integration.ts`, from the transaction's own table counters; a reviewer reproduced the 500). That row count is the claim. End-to-end times depend on the machine and its load: the developer measured, with against without bills, 723 against 254 ms to post and 770 against 513 ms to alter before 0009, and 205 against 120 ms and 419 against 361 ms after; a reviewer with a probe running alongside measured 809 against 359 ms and 1,371 against 772 ms. Neither the times nor their ratios are stable figures.
- **Bill lists and statistics.** A page of bills receivable or payable seeks to its cursor through `bill_ledger_order_idx` on `bill.name_key` (the match key stored with the bill, migration 0009: under the forced row-level policy only leakproof comparisons become index conditions, and `name_match_key` is not, so a keyset on the expression was a filter), reads each bill of the page by its id (`bill_id_idx`) and finds the parties with bills by a semi-join by ledger. What it reads depends on the statistics of `bill`. With current statistics a page reads about its own bills, at any depth. Without statistics (a new installation, until autovacuum or `ANALYZE` runs), or with statistics older than the company's bills, a page may read up to the company's bills: once for the parties check, plus the party's bills from the cursor to the party's end. It never reads another company's bills, and never the table. Measured on one fixture (a page of three of a party with 300 bills, in a company of 304 to 307 bills beside another company with 1,500 to 3,000; `tests/bills-page.integration.ts`, `tests/bills-page-stale.integration.ts`, the transaction's own table counters, no planner setting changed), not guarantees: everything analysed, 10 to 21 bills read at any depth; `bill` analysed only, 32 to 42; nothing analysed, 305 to 325 bills at the start of the party, 230 in the middle, 26 to 39 near its end; the joined tables analysed but not `bill`, 607, 512 and 317 (the parties check reads the company's bills once); statistics taken before the company's bills arrived, 12 to 329. Not fixed in 0009: a planner setting would be needed to make the planner walk the index in order.
- **The stored bill key follows `name_match_key` as it was written.** If a later migration redefines `name_match_key`, the stored keys (`bill.name_key`) do not recompute until that migration rewrites `bill` (for example by updating every row's name to itself or rebuilding the column), and it must check the new keys for clashes as 0009 does.
- **M1's voucher check is quadratic in the line count.** It runs on every voucher and line event and reads the whole voucher each time (M1's design, unchanged here). Measured medians on the verifier's machine for a 500-line voucher: post 102 ms and alter 203 ms without bills (M1 alone: 100 and 194), and 348 ms and 629 ms with 250 bills; the per-line re-check is 233 ms of that alter and grows with the square of the line count. Not optimised in M2a slice 1.
- **Cost rows on a 500-line voucher.** A 500-line journal with a row in each of two categories on every line (1,000 rows) against the same voucher without rows, end to end over the API, medians of three: one developer machine measured 278 ms against 134 ms to post and 567 ms against 345 ms to alter; the reviewer's busier machine 788 against 183 ms and 1,420 against 419 ms. These are one machine's figures each; the stable figure is the ratio, about 2 to 4 times the post and 1.6 to 3.4 times the alter without rows. The deferred cost checks themselves took 106 to 199 ms at the post and 281 to 548 ms at the alter (2,000 row changes) on both machines. `tests/cost-centres-timing.integration.ts` checks with the transaction's own table counters that the 1,000 checks fetch exactly 2,000 rows by index and scan nothing.
- **The revision log's entity check is added `NOT VALID`** by migration 0008: it only widens the earlier check, so existing rows pass it, and validating it inside the migration would scan the log under an exclusive lock. New rows are checked as before.
- **Migration 0010 refuses master names the key makes one.** Names of one company's groups, ledgers, voucher types, cost categories or cost centres that were apart under lower-case comparison and are one name under the key stop the migration, and nothing is applied; the operator sees `PostgreSQL error P0001` and the server log names the table, the company and the names. The same list, per table, comes from this query run as a superuser before migrating (shown for ledgers; replace the table for the others): `SELECT company_id, string_agg(name, ', ' ORDER BY name) FROM ledger GROUP BY company_id, lower(translate(name, E' \t-./,()+*;=~?{}&', '') COLLATE pg_c_utf8) HAVING count(*) > 1;`. The operator renames those masters and migrates again. The migration holds exclusive locks on the five master tables while it rebuilds their name indexes.
- **Currency checks and statistics.** The symbol and code checks, the decimals and delete checks and the rate lookup are index lookups led by the sought column (`currency_symbol_idx` on the stored key, the primary key by code, `ledger_currency_idx` on `(currency, company_id)`, the rate primary key), and the guards plan them with their values each time (`EXECUTE`): the same lookup as static PL/pgSQL reads no ledger for five runs in a session and then, on its cached generic plan, the table's ledgers (506 rows, with statistics, almost every ledger in the base currency; `tests/currencies-plans.integration.ts`), while the guard reads none. Measured with the transaction's own table counters over seven runs in one session, beside another company with 400 currencies, 400 ledgers and 2,400 rate rows (`tests/currencies-guards.integration.ts`, no planner setting changed): with statistics each check reads at most 2 rows and the lookup one rate row per currency and kind with rates. Without statistics (a new installation, until autovacuum or `ANALYZE` runs) the two symbol lookups may go through the primary key with the company as their only condition and read the company's currencies, twice (133 rows for a company of 66), never another company's; the other checks stay at 2 rows. Harmless at currency-list sizes; not fixed in 0012 (a planner setting would be needed). A currency delete's foreign-key checks read every voucher line, bill and bill row of the table by sequential scan, not only the company's: their `currency` columns have no index. Accepted for a rare master delete; slice b decides that index with its own access paths.
- **Master lists ordered by lower-case name read no index in order.** The name indexes are on the key since 0010, so a list ordered by `lower(name)` sorts the company's masters of that kind; harmless at master-list sizes.
- **Migration 0009 refuses bills the new key makes one.** Two bills of one party that differ only by ignored characters (AB1 and A-B1) were two bills before 0009 and are one under its match key; the migration does not merge them silently but stops, and nothing is applied. The operator sees `PostgreSQL error P0001` (the migration runner reports only the SQLSTATE); the database server's log has the error with the company, the party and the spellings (an `ERROR` line from the migration transaction). The same list comes from this query, run as a superuser before migrating: `SELECT company_id, ledger_id, string_agg(name, ', ' ORDER BY name) FROM bill GROUP BY company_id, ledger_id, lower(translate(name, E' \t-./,()+*;=~?{}&', '') COLLATE pg_c_utf8) HAVING count(*) > 1;`. The operator renames or merges those bills by hand and migrates again. No released installation holds bills yet.
- **Locks while 0009 runs.** The migration holds exclusive locks on `bill`, `bill_allocation` and `voucher` for its whole transaction and builds two indexes under them. Harmless before release; on a live installation it needs a planned window.
- **The name match key follows the server's Unicode tables.** Its lower-casing (`pg_c_utf8`) uses the Unicode version of the PostgreSQL major release, so a major upgrade may change the key of rare characters and require rebuilding `bill_identity_idx` (`REINDEX`) and checking it for clashes. The TypeScript twin follows Node's tables, which may be newer (28 code points differed when 0009 was written); the database's key is the authority for identity, the twin only matches names in lists.
- **Removing a company with posted vouchers fails** on M1's line-to-ledger key (no route removes a company yet). Cost categories, centres and their guards let a removal through; rows on vouchers could not be exercised for that reason.
- **The opening-bill check is quadratic in a ledger's opening bills.** It runs at commit for every inserted or deleted opening row and sums the ledger's opening rows each time, so a ledger with many thousands of opening bills is slow to save. Ordinary openings hold a handful.

## Not in M1

No report read models beyond the trial balance and ledger balance; no inventory lines, foreign-currency bills, interest on bills, credit limits, multi-currency posting or tax computation (the columns exist and stay empty); no user-created voucher types or extra numbering series; no manual numbering or renumbering, no restart periodicity other than yearly, no change to the restart rules, and no prefix, suffix, number width or numbering method (D-04); no audited unlock of a locked period (the locked-through date is set outside the API for now); no conversion job for post-dated vouchers; no maintained period-balance table (D-04 benchmark pending). Requirement status follows D-01: none of this is described as equivalent to any other product.
